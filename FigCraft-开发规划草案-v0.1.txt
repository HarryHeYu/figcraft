# FigCraft — MVP 开发规划与第一版技术方案

项目设计草案 v0.1 · 2026 年 10 月 24 日

项目名称： FigCraft

项目定位： Agent-Native Scientific Figure Studio

一句话介绍： An agent-native, programmable scientific figure engine that turns structured descriptions into publication-ready, editable vector graphics.

核心原则： Figures as Code, Agents as Artists.

FigCraft 不应该只是又一个“输入 Prompt → 生成科研图片”的工具，而应该是一套能够被 Coding Agent 调用的科研绘图引擎、结构化编辑系统和质量检查工具链。

最终希望实现这样的用户体验：

```
# 新建一个科研图工程
figcraft init figures/method

# 根据结构化描述生成图形
figcraft render figures/method/figure.json \
  --format svg,pdf,pptx

# 检查投稿质量
figcraft lint figures/method/figure.json

# 使用统一布局重新排版
figcraft layout figures/method/figure.json \
  --preset two-column
```

Agent 可以在这套命令之上，通过 MCP 工具创建节点、连接模块、修改标签和调整排版，而不用每次重画整张图。

### 明确不做的内容

v0.1 不做网页版画布、不做自己的 AI 模型、不做任意图片到完美 SVG 的逆向重建、不做任意 SVG/PPTX 的双向无损导入，也不做完整的 TikZ 编译器。

这些目标很容易让一个小项目变成庞大的图形软件工程。首先把原生图形生成、精准编辑和多格式导出做好更重要。

## Figure IR

唯一可信的图形源数据

Nodes

Edges

Groups

Styles

Layout + Geometry + Lint

确定性布局、文字测量、连线与边界检查

SVG Renderer

PDF Exporter

PPTX Renderer

这里有个关键决定：

Figure IR 是源文件；SVG、PDF 和 PPTX 都是构建产物。

生成的 PPTX 可以交给作者修改，但在首版中，不承诺能把 PowerPoint 内的修改无损同步回 Figure IR。否则很快会陷入复杂的双向格式转换问题。

另外，Agent 修改文件时应通过语义化 Patch，而不是直接修改任意 XML 或 PowerPoint 内部文件。

例如，Agent 想把一个模块从蓝色改成橙色，只需要调用：

```
{
  "op": "set_style",
  "target": "forget_branch",
  "style": {
    "fill": "#FCE4CF"
  }
}
```

它不需要重新生成整个流程图。

## 四、Figure IR v0.1 规范

第一版建议采用 JSON 作为交换格式、磁盘源文件格式，并使用 Pydantic 进行严格校验。

### 最小数据模型

| 对象     | 关键字段                                                | 说明           |
| ------ | --------------------------------------------------- | ------------ |
| Figure | schema_version, canvas, nodes, edges, theme         | 顶层图形         |
| Canvas | width, height, unit, margin                         | 物理画布尺寸，单位 mm |
| Node   | id, type, x, y, width, height, label, style         | 图形元素         |
| Edge   | id, source, target, source_port, target_port, style | 带语义连接关系的边    |
| Group  | id, children, label                                 | 逻辑分组         |
| Theme  | font_family, font_size, palette                     | 全局视觉规范       |

首版所有几何坐标都采用毫米，字号采用 pt。内部统一换算，不能在不同渲染器里各自推测单位。

### 示例：一个真正可用于实现的图形定义

```

  "id": "method_pipeline",
  "canvas": {
    "width": 182,
    "height": 58,
    "unit": "mm",
    "margin": 4
  },
  "theme": {
    "font_family": "Arial",
    "font_size_pt": 8,
    "background": "#FFFFFF"
  },
  "nodes": [
    {
      "id": "input",
      "type": "rounded_rect",
      "label": "Input Video",
      "x": 5,
      "y": 18,
      "width": 38,
      "height": 20,
      "style": {"fill": "#E8F0FE", "stroke": "#4275C4"}
    },
    {
      "id": "encoder",
      "type": "rounded_rect",
      "label": "Video Encoder",
      "x": 61,
      "y": 18,
      "width": 48,
      "height": 20,
      "style": {"fill": "#E5F4EC", "stroke": "#418968"}
    },
    {
      "id": "output",
      "type": "rounded_rect",
      "label": "Prediction",
      "x": 127,
      "y": 18,
      "width": 48,
      "height": 20,
      "style": {"fill": "#FCE8D8", "stroke": "#C17C43"}
    }
  ],
  "edges": [
    {
      "id": "e_input_encoder",
      "source": "input",
      "target": "encoder",
      "source_port": "right",
      "target_port": "left",
      "style": {"stroke": "#444444", "arrow": "end"}
    },
    {
      "id": "e_encoder_output",
      "source": "encoder",
      "target": "output",
      "source_port": "right",
      "target_port": "left",
      "style": {"stroke": "#444444", "arrow": "end"}
    }
  ],
  "groups": []
}

```

首版的 `x/y/width/height` 是确定的渲染坐标。自动布局时由布局器生成或更新这些数值，再交给三个导出后端消费。

这样不会出现 SVG、PDF 和 PPTX 各自重新计算布局，导致导出形态不一致的问题。

### 结构化修改的规则

必须从第一版就定下来：

- 所有对象具有稳定、唯一的 ID；修改样式不得改变 ID。
- 禁止悬空连接；删除节点时必须显式处理相连的边。
- Patch 操作先验证、后提交；失败时不能留下半张损坏的图。
- 同一份 IR、同一字体环境和同一渲染器版本应产生确定性的布局与 SVG 输出。
- 保留 `schema_version`，以后才能平滑迁移格式。

## 五、MCP 与 Agent API 设计

首版 MCP 工具控制在 7 个，不要把每一种小操作都暴露成单独工具。

| MCP Tool           | 用途                  |
| ------------------ | ------------------- |
| `figcraft_create`  | 创建 Figure 项目        |
| `figcraft_get`     | 读取当前图形及其对象          |
| `figcraft_patch`   | 批量新增、修改、删除图元        |
| `figcraft_layout`  | 自动排列节点、重新计算连线       |
| `figcraft_render`  | 导出 SVG / PDF / PPTX |
| `figcraft_lint`    | 返回图形质量问题            |
| `figcraft_inspect` | 获取对象位置、尺寸、关系和属性     |

其中最重要的是 `figcraft_patch`。它应该支持多个操作在同一事务里提交，并在操作失败时提供明确原因。

### Agent 交互示例

用户：

> 给我画一个 LLaVA 的模块级 Unlearning 框架图，包含视觉编码器、连接器、LLM、Forget 和 Retain 两条分支。

Agent 先构造布局和节点，然后调用 FigCraft MCP。

首次创建后，返回结构化结果：

```
{
  "figure_id": "llava_unlearning",
  "revision": 1,
  "nodes": 8,
  "edges": 9,
  "status": "valid"
}
```

用户接着要求：

> 把视觉编码器和连接器用虚线框成一个组，然后把 Forget 分支改成橙色。

Agent 只需对已有项目执行 Patch。接口采用 `expected_revision` 避免多个 Agent 同时编辑时互相覆盖。

```
{
  "figure_id": "llava_unlearning",
  "expected_revision": 1,
  "operations": [
    {
      "op": "add_group",
      "id": "visual_stack",
      "children": ["vision_encoder", "connector"],
      "style": {"stroke_dash": "dashed"}
    },
    {
      "op": "set_style",
      "target": "forget_branch",
      "style": {"fill": "#FCE4CF"}
    }
  ]
}
```

成功后版本更新至 revision 2。渲染器再重新导出。

特别重要： 不允许 Agent 直接向 IR 任意字段写入未经验证的数据。所有操作都必须经过 Schema 验证和对象完整性检查。

### Agent Skill

Skill 不承担核心引擎的实现，只负责指导 Agent 如何使用 FigCraft。

应该覆盖四个流程：

1. 从方法描述抽取模块和依赖关系。
2. 生成一个合法且简洁的 Figure IR。
3. 调用布局、渲染和 Lint，根据错误定向修改。
4. 在质量检查通过后交付多格式产物。

首版应该先提供跨平台的 CLI Skill，再开发 MCP 集成，这样可以复用已有能力，减少调试难度。

### 我建议采取的实现顺序

不要同时让多个 Agent 修改核心模块。先建立 M0 的 Schema 和统一接口，再并行开发彼此独立的渲染器和测试。

等到 SVG 和 PPTX 都能正确表达同一个 Figure IR，才开始大规模接入 Agent。

原因是 FigCraft 最复杂的地方不是 MCP 或 CLI，而是图形几何、文字尺寸、连线定位和跨格式一致性。

## 八、质量检查与验收标准

这是 FigCraft 与普通 AI 绘图脚本拉开差距的重要模块。

### Figure Lint v0.1

| 规则    | 严重程度    | 检查内容        |
| ----- | ------- | ----------- |
| FC001 | Error   | 节点越过画布边界    |
| FC002 | Error   | 重复 ID 或无效连接 |
| FC003 | Error   | 文本超出节点边界    |
| FC004 | Warning | 非预期节点重叠     |
| FC005 | Warning | 正文字号低于配置阈值  |
| FC006 | Warning | 箭头穿过非关联节点   |
| FC007 | Warning | 字体无法解析或发生替代 |
| FC008 | Warning | 存在未经声明的栅格图像 |

需要为错误定义清楚的计算方式。比如文字溢出要使用字体度量，不能通过简单的“字符数 × 平均宽度”来判断。

对于自动布局，还要支持允许重叠的合法场景，比如子节点位于组背景内部。

### v0.1 发布验收

Release Gate

0/8 项

Figure IR 能正确验证合法与非法输入

同一份 IR 可以导出 SVG、PDF 和 PPTX

SVG/PDF 图元非栅格化，PPTX 的框、文本和箭头可编辑

三种示例图均无严重溢出和误连接

对单节点改色后，其余节点属性保持不变

错误 Patch 不修改原文件和 revision

Agent 无人工修改 JSON 即可完成一次创建、修改、导出

Windows、macOS、Linux 的自动化测试通过

这是待执行的验收清单，不表示当前项目已经通过测试。

除了这些测试，我建议额外设立三个工程要求：

第一，视觉回归。 把 SVG 渲染为 PNG 做快照比较；像素差异用于发现回归，但需要结合平台字体差异，不能单纯依赖完全相同的像素哈希。

第二，跨格式一致性。 对同一个图元检查 SVG 和 PPTX 的位置、尺寸、颜色和文本内容。设定几何坐标误差阈值，例如 0.2 mm；文字排版则单独做视觉检查。

第三，安全性。 MCP 只能读写配置允许的工程目录；默认不读取任意外部文件，不通过 SVG 加载远程资源，不执行图形描述里包含的脚本。

尤其不应该让通过 MCP 传入的输出路径直接覆盖用户其他项目文件。

## 九、第一轮开发：可以直接交给 Coding Agent 的任务书

下面这段是我建议直接发给 Codex、Claude Code、OpenCode 或 DeepSeek Harness 的初始开发指令。

# FigCraft — v0.1.0 MVP 开发任务书

你是一名资深 Python 工程师、图形系统工程师和开源项目维护者。

请从零实现一个名为 **FigCraft** 的开源项目。

## 1. 项目定位

FigCraft = Agent-Native Scientific Figure Studio。

目标是让 Coding Agent 使用结构化图形描述，创建、修改、检查和导出科研论文中的高质量矢量图。

核心理念：

- Figures as Code
- Figure IR as the single source of truth
- Deterministic rendering
- Incremental semantic editing
- Agent-native interfaces
- Publication-ready exports

不要实现普通的 Text-to-Image 工具，不要依赖图像生成模型直接输出最终论文图。

## 2. 环境和工程要求

- Python 3.11+
- uv + pyproject.toml
- Pydantic v2
- Typer + Rich
- python-pptx
- CairoSVG
- MCP Python SDK v2
- pytest + pytest-cov
- 采用 src-layout
- 支持 Windows / macOS / Linux
- 使用类型标注、清晰的模块边界和规范的错误处理
- 不要在系统盘生成大型临时文件
- 所有输出放在用户指定的项目或构建目录
- 锁定依赖，并验证依赖 API，不复制过时的 MCP 示例

## 3. 必须实现的模块

### Core

实现版本化的 Figure IR 数据模型，至少包含：

- Canvas
- Node
- Edge
- Group
- Style
- Theme
- Figure

实现 JSON 加载、保存、验证、唯一 ID 检查、连接引用检查。

坐标使用 mm，字号使用 pt。定义统一的内部转换函数。

### Patch

实现语义化 Patch 引擎，支持：

- add_node
- remove_node
- update_node
- set_style
- add_edge
- remove_edge
- add_group
- update_label

采用稳定 ID 和 revision，支持多个操作一次性提交。

保证事务性：任意操作失败时，原文件保持不变。写入使用临时文件加原子替换；对跨进程同时写入提供文件锁或等效机制。

### Layout

实现：

- horizontal layout
- vertical layout
- basic layered layout
- orthogonal edge routing
- center/left/right/top/bottom ports

布局必须确定性，不依赖随机顺序。

### Renderers

实现 SVG、PDF、PPTX 三种输出。

SVG 使用原生矢量元素，保持文本元素可编辑。

PDF 从 SVG 矢量转换，不通过 PNG 中转。测试字体和矢量保留情况。

PPTX 必须使用原生形状、文本框及连接线，不能将整个图作为图片插入。

三个渲染器共用 Figure IR 和最终几何布局。

### Lint

至少实现：

- 画布溢出
- 无效 ID 或连接
- 文字溢出
- 非预期节点重叠
- 字号阈值
- 非法颜色
- 不支持的字体

返回机器可读取的 JSON 结果，包含规则 ID、严重程度、相关对象 ID 和描述。

对无法可靠检查的规则，不要假装已经完成检测。

## 我的最终建议

FigCraft v0.1.0 的真正完成标志，不是写了多少代码，而是一个从头到尾的真实 Agent 测试：

给 Agent 一段没有图的论文方法描述，让它生成图；接着连续要求修改布局、颜色、文字和分组；最终输出 SVG、PDF、PPTX，所有产物有效、无严重布局问题，且未指定修改的对象保持不变。

如果这个场景能稳定跑通，FigCraft 就不仅仅是一个绘图脚本，而是一个具备独立价值的 Agent 工具。

我建议把 结构化编辑的可靠性、出版级矢量导出和 Figure Lint 作为最早的三个卖点。网页版和更复杂的 AI 绘图能力可以留到 v0.2 以后。
